## Instruction to each reviewer

Review the reusable evidence-only agent harness and its Sanctum integration against `claude-code-harness-spec.md`, `pdlc-claude-code-pilot-plan.md` and `pilot-0-readiness.md`. This is a research pilot using synthetic artifacts, not a production approval. Review once; do not delegate, edit implementation, or launch paid trials. Write only your review report. Preserve material disagreements with the plan rather than assuming every checklist claim is true.

Inspect implementation and concrete saved outputs. Distinguish implemented code, exercised transport, independently accepted data, activated memory, model identity and task-quality evidence. A passed fixture or one model connectivity call cannot establish agent benefit, general ACL safety or hosted Claude availability.

### Review pillars

1. **Decision question and fair comparison.** Does direct access let Claude choose and iterate? May both arms retrieve repeatedly? Verify actual common turn, delivered-evidence, deadline and spend limits; count repeated evidence, metadata and nested System One overhead. Inspect normalization, omission/exhaustion, concurrent delivery, failed/undispatched denominators, task-level pairing and scope strata. Could successful refusals or fixture runs mask poor supported answers?
2. **Trust and access boundaries.** Follow caller binding from controller through agent MCP, ProcessSUT, proxy, gateway and hub read. Try to find an agent-controlled token, request identity, metadata, source/provider option, file path or policy input that crosses the boundary. Verify live artifact authorization before ABOUT use, exact version/hash matching, unknown-subject handling, revocation/deletion and release coherence. Identify limitations of uniform pilot visibility separately from proven general authorization. Do scoped delegations actually prevent a review from granting itself authority? Are proposer and approver identities honestly recorded?
3. **Actual Claude execution.** Inspect native probe events, tool allowlist, bare/restricted options, clean home/workspace, inherited canaries and forbidden tool results. Does native turn counting agree with installed CLI termination? Check descendant and in-flight cleanup, durable dispatch records, cancellation and replay refusal. Does a native error, exhausted budget, absent retrieval or malformed result remain an incomplete task? Verify the evidence behind the exact model identifier and low effort.
4. **PDLC task/scorer validity.** Inspect the thirty-task matrix, representative evidence/gold and all scorer fixtures. Check grounding against pinned code/design/procedure/session records, mistaken absence claims, repeated facts/reasoning, supported/partial/out-of-scope labels and explicit HLD/LLD demands. Could literal matching, a declared-claim loophole, irrelevant citations, unsupported extras, contradictory prose, invented thresholds or generic refusal earn credit? Are alternative sound designs allowed, with existing-system facts distinguished from proposals? Are human acceptance, provisional judgment and independent gold ownership kept distinct?
5. **Pins, interfaces and failure behavior.** Check config/corpus/task/gold/runtime/template/calibration/delegation hashes and containment. Follow changed versions, stale semantic receipts, ambiguous artifact IDs, source interface differences, invalid configurations and missing releases. New graph-backed operation must not silently fall back to legacy lexical subject matching. Old lab controls must remain identifiable controls rather than evidence that new memory works.
6. **Resource accounting and reproducibility.** Verify pre-dispatch reservations, attempt-local broker call/input caps, retries, missing usage, pricing assumptions, unknown-cost stopping and reconciliation. Reservation estimates are not actual costs. Check saved answers, native events, delivered passages, provider traces, report/result/ledger consistency and seeded schedule/bootstrap. Distinguish localhost SDK cost estimates from charged inference.
7. **Reuse and implementation scope.** Exercise or inspect PDLC plus an unrelated bundle without repository-name branches in the controller. Require the Sanctum connection as well as direct-hub proof for the complete reuse claim. Claude is the first adapter; later Codex/Pi and local editing loops are deferred. Flag unnecessary mechanisms only when a simpler existing component preserves the requested behavior and failures.
8. **Coverage and readiness.** Map each remaining goal/plan gate to direct evidence. Name what tests actually prove and what they miss. Do not fabricate business-owner approval, human adjudication, an approved paid budget, frozen gold or production deployment. Unavailable inputs may be readiness blockers even if the corresponding implementation is correct; separate those from repairable code defects.

## Output contract

Return a recommendation: `ready_for_unpaid_preparation`, `repair_required`, or `ready_for_separately_budgeted_trial`, with its limits. List findings by severity, each with file/line, concrete failing sequence, user/research consequence, evidence and the smallest correction preserving the goal. Mark each as an implementation blocker, data/policy acceptance gate, missing verification, or follow-on work. Include test gaps and any uncertainty. Explicitly record if there are no findings in a pillar; do not treat lack of inspection as a pass.

Do not run a second review loop. The coordinator will collate both reports, preserve disagreements, fix blocking implementation issues and run targeted verification. Reviewer conclusions alone do not approve operational policy or paid dispatch.
