# Corpus authoring

Preparation only: these synthetic author packets are not hub corpora or benchmark answers. The generation runner will read the selected provider key from the gitignored lab `.env` or `GEMINI_API_KEY` / `OPENAI_API_KEY`, never include it in saved prompts, and use a total preparation ceiling of $20. Model selection, current pricing and per-call reservations must be recorded before dispatch.

Each packet supplies only one author's local knowledge. Preserve raw model outputs and introduced-claim manifests in a private build directory. Audit code behavior, source applicability and provenance before packaging accepted text into hubs. Do not give benchmark questions to generation calls.

The [corpus specification](../../docs/experiments/pdlc-corpus-spec.md) defines the initial inventory and private scenario ledger. The runtime must never read this authoring directory.

The runner retries HTTP 429 and 503 up to three times per packet, with exponential backoff and equal jitter (15–30 seconds, then 30–60 seconds, capped at 60). It checks the preparation cap and reserves each attempt separately, retains unresolved reservations, and skips completed packets. Longer or nonnumeric Retry-After headers stop for a later resume. Other errors stop without automatic retry. Use `--retry-rejected` to resume a prior rejected packet; `--max-retries 0` disables automatic retries.

Select `--provider gemini --model gemini-3.8-flash` or `--provider openai --model gpt-6-luna`. OpenAI uses Responses JSON mode with medium reasoning. Packet prompts and acceptance checks are shared. Both providers use the same $20 ledger; OpenAI reserves $0.02 per attempt (32,000 input bytes plus API overhead and 16,384 total output tokens at pinned prices), Gemini retains its conservative $1 reservation. Completed packets with matching prompt hashes are reused across providers. No automatic provider or model substitution occurs.

Project `.env` credentials take precedence over inherited environment variables; missing local values fall back to the environment. Keys are never included in generation prompts, responses or ledger entries. An interrupted request retains its reservation.

Structured hierarchy jobs use `--job-file <jobs.json>`, with `{ "jobs": [{ "name": "safe-id", "prompt": "...", "schema": optional_JSON_Schema }] }`. They share the same credential selection, provider adapters, retry policy and preparation ledger; results are retained as `*.result.json` alongside raw responses and prompt hashes. `--max-output-tokens 32768` reserves $0.04 per OpenAI attempt, covering the bounded input plus output tokens at pinned prices. Artifact generation remains unchanged.

Hierarchy preparation and validation: `python3 tools/map_pdlc_hierarchy.py prepare-catalog`, generate its catalog jobs, `prepare-mappings`, generate the mapping jobs, `prepare-ownership`, generate its ownership job, then `prepare-repairs` when exact quotation checks identify errors, generate its strict quote-patch job, and run `validate`. The final private manifest is `build/pdlc-authoring/pdlc-hierarchy.json`. Exact source quotations carry metadata/text field and character spans; full mapping coverage, acyclic parents, typed references, preserved paths/versions and proposed container ownership are checked. Source review/session metadata can support classification; private introduced-claim manifests cannot. LLM output is a candidate until validated. Evidence-only patches may repair quotations without changing source contents or structural assignments.

Audit resolution: `python3 tools/resolve_pdlc_audit.py` builds `pdlc-audited-candidate.json` without modifying raw responses. It includes audited source content, corrected hierarchy, finding dispositions, private gold constraints and verification scope. It is not a runtime payload; private fields must be excluded during packaging.

Pilot loading: `PYTHONPATH=src .venv/bin/python tools/ingest_pdlc_corpus.py` writes only `build/pdlc-pilot`, without changing the base world. `PYTHONPATH=src .venv/bin/python tools/verify_pdlc_ingestion.py` launches the existing stdio hubs, verifies all 96 reads plus search/citation/access boundaries, and writes a private verification report. This is a development candidate, not a frozen benchmark corpus. No model inference is used.

## Ontology harvesting pipeline

`PYTHONPATH=src .venv/bin/python tools/harvest_pdlc_memory.py run --provider openai --model gpt-6-luna` runs inventory → MCP fetch → structural candidates → bounded LLM proposals → evidence validation → memory projection/review packet. Gemini 3.8 Flash remains selectable; generation uses the existing shared cap, retries and receipts. Completed compatible jobs resume without paid regeneration. Individual stages are `harvest`, `jobs` and `assemble`; generation jobs are in `build/pdlc-memory/semantic.jobs.json`.

`src/sanctum_ref/harvest.py` owns the source-neutral connector contract and proposal/review validation. Connectors supply paged inventories, explicit access-context completeness, stable snapshot IDs, normalized records and native capabilities. The pilot adapter uses the complete public local hub corpus as inventory and retrieves source bodies through actual MCP tools. Search results are not a complete inventory; an actual remote source needs its own native enumeration/export adapter. No generic remote integrations are claimed. Connectors must independently establish metadata visibility, native identifiers and version semantics; synthetic pilot visibility is explicitly one reader/group.

Outputs stay separate from active lab memory: `build/pdlc-memory/candidate.json`, `review-template.json`, `owner-declarations-template.json`, `summary.json` and content-addressed `releases/<id>/release.yaml`. Public hub structure/content is the only harvesting input; private generation manifests, gold and evaluation tasks are excluded. Raw model hashes and completed prompt receipts are checked before projection. Four nonliteral evidence proposals from the first run were quarantined rather than patched into acceptance.

`assemble --declarations <file>` accepts explicit owner declarations under `declarations`: each record names `source_id`, `owner`, optional `visibility_groups`, `memberships` (`entity_id`, `parent_id`), `authority` (`entity_id`, `fact_kind`) and `procedures` in the existing trigger/action grammar. All become proposed with declaration hashes and provenance. Actual selectors are checked against harvested structure/capabilities. No inference from placement into membership or from business instructions into routing policy occurs.

`assemble --review <file>` requires a named reviewer, exact candidate `snapshot_hash` and assertion-ID decisions (`accepted`/`rejected`). Unmentioned assertions stay proposed. Reviewed ontology and authority records are retained separately; the memory projection includes reviewed names, filters, membership, routing procedures and subject bindings. Neither path changes ACTIVE. Releases are content-addressed by candidate, review and projector version, and existing release contents cannot be overwritten.

Both reference memory backends now expose provenance-backed, accepted-only `subjects_for(...)`, requiring exact source/artifact/version/content hash and visible group/principal scope. Missing, stale or inaccessible bindings remain unknown; ABOUT never establishes identity. Wiring this API into runtime evidence assembly and the pilot registry remains part of integration. No new EvidenceResponse wire fields or production connectors were added.

Domain supplements: `tools/extend_pdlc_procedures.py prepare` prepares grounded procedure jobs; use the shared generator, source-review the results, then `apply` builds the separate expanded candidate. `tools/ingest_pdlc_corpus.py --candidate build/pdlc-authoring/pdlc-expanded-candidate.json` loads 102 records; rerun `verify_pdlc_ingestion.py` and the ontology pipeline after public source changes. The six new procedures remain drafts awaiting business review.
