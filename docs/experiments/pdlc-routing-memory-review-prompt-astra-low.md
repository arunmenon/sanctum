No implicit closure, storage-derived membership, place-derived identity or authority inferred from a document calling itself HLD. Stable concepts/instances and native names must remain distinct.
2. **Semantic grounding and false bindings.** Verify all assertion provenance mechanically where possible, then inspect meaningful bindings against full source context. Quotes must entail the specific proposed relationship, not merely mention an entity. Check generic Auth ambiguity, similarly named payment versus batch fraud clients, identity versus payment authorization, historical/proposed/current versions and multi-subject artifacts. New design drafts must not create approved aliases, deployed-service relationships or accepted implementation claims. Look for common boilerplate causing spurious cross-domain links.
3. **Hierarchy and routing usefulness.** Inspect repo/document-space/module navigation, cross-links and source-native selectors. Does the graph preserve artifact-specific subjects rather than label an entire repo as one entity? Are filters executable against current hub capabilities/locations? Are omissions explicit rather than hidden by assertion counts? Walk at least payment timeout, identity provisioning and ledger batch/posting neighborhoods, distinguishing useful proposed retrieval routes from actual operational capability.
4. **Scope, authorization and lifecycle.** Distinguish one-principal synthetic fixture coverage from general permission correctness. Check artifact/version/hash binding, independent metadata visibility, scope-filtered identities/descriptors/selectors, live ACL/unshare/revocation behavior, renamed/deleted records and complete versus incomplete inventories. A frozen source snapshot must not freeze access. Proposers cannot approve; owner/reviewer declarations must enforce delegated scope rather than trust arbitrary labels.
5. **Release integrity and runtime integration.** Check a request can eventually pin one coherent immutable memory/registry/authority/descriptor/procedure/calibration dependency set. Inspect projection behavior for proposed/rejected/accepted/unknown records, cache keys and rollback requirements. Report actual source-to-subject API wiring and missing evidence assembly. Assert no ACTIVE was written and no proposal affects routing today. Confirm System One can rank/select without establishing identity or inventing observation history.
6. **Reproducibility, quarantine and implementation proportionality.** Reconcile corpus/source/candidate/release hashes and counts, prompt/response receipts, exact versions and citation coordinates, unknown subjects/coverage and five rejected proposals. Check repeat runs, source changes and duplicate versions for contamination. Inspect whether rejection evidence is retained meaningfully. Evaluate targeted tests including failure cases, and identify the smallest necessary fixes; do not propose a new graph database or control plane without a concrete requirement.
